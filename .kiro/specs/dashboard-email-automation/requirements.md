# Requirements Document

## Introduction

This specification covers five enhancements to the existing RSOB Quality Performance Dashboard — a self-contained static HTML file generated by `scripts/build-static.ts` and deployed to Netlify. The dashboard embeds all audit data inline and runs entirely client-side with no server. The enhancements are: (1) week-wise breakdown of common findings, (2) email automation with feedback tracking for managers/admin, (3) EMS portal deep-linking for repeated outliers, (4) a leadership analysis report for admin, and (5) the localStorage-based feedback tracking state machine. All changes are implemented within the build script that produces `dist/dashboard.html`.

## Glossary

- **Dashboard**: The self-contained static HTML file (`dist/dashboard.html`) generated by `scripts/build-static.ts`, embedding all audit data and rendering entirely client-side.
- **Build_Script**: The TypeScript file `scripts/build-static.ts` that reads `data/audit-records.json` and `data/role-mapping.json`, then generates the static Dashboard HTML.
- **Associate**: An individual contributor whose audit records are tracked, identified by `associateLogin`. Associates see only their own data.
- **Manager**: A supervisor identified by `supervisorLogin` who sees data for all associates reporting to them. There are 23 managers in the current role mapping.
- **Admin**: The system administrator (`mpuranik`) with unrestricted access to all data across every associate and manager.
- **Audit_Record**: A single row from the audit dataset, containing region, transaction week, transaction date, associate login, supervisor login, disruption type, five quality attribute pass/fail results (ADM, RA, RRC, ACC, RV) with findings, and a defect flag.
- **Quality_Attribute**: One of five audited dimensions — ADM, RA, RRC, ACC, RV. Each is "Yes" (pass) or "No" (error).
- **Defect_Rate**: The percentage of Audit_Records that are defects within a given scope, calculated as `(totalDefects / totalAudited) * 100`.
- **Common_Findings**: Distinct auditor finding texts grouped by Quality_Attribute, with frequency counts, extracted from Audit_Records where the attribute is "No".
- **Transaction_Week**: The week number assigned to each Audit_Record (e.g., 11, 12, 17), used as the primary time dimension.
- **Mailto_Link**: A `mailto:` URI scheme that opens the user's default email client (Outlook on corporate machines) with pre-filled recipient, subject, and body fields.
- **Feedback_Tracker**: A client-side state store using `localStorage` that persists per-associate email sharing status (Pending or Shared) scoped to the logged-in manager and selected week.
- **EMS_Portal**: The external SharePoint-based Employee Management System at `share.amazon.com` used to file performance actions for repeated outliers.
- **EMS_Link**: A URL constructed with query parameters that opens the EMS_Portal new-item form with pre-filled fields (Team, Week, Associate, Manager, Region, Category, Case IDs, Summary).
- **Repeated_Defaulter**: An associate with confirmed defects in 3 or more of the last 5 rolling Transaction_Weeks.
- **Leadership_Report**: An admin-only formatted section containing a comprehensive cross-region performance analysis suitable for sharing with leadership.
- **Clipboard_API**: The browser `navigator.clipboard.writeText()` API used to copy formatted report content to the system clipboard.

## Requirements

### Requirement 1: Week-wise Common Findings Breakdown

**User Story:** As a dashboard user (associate, manager, or admin), I want to see common findings broken down by week, so that I can identify which errors are occurring in which specific weeks rather than only seeing an aggregate view.

#### Acceptance Criteria

1. WHEN the Common Findings section is rendered, THE Dashboard SHALL group findings by Transaction_Week and then by Quality_Attribute within each week, instead of aggregating across all selected weeks.
2. FOR each Transaction_Week in the selected filter range, THE Dashboard SHALL display the distinct auditor finding texts and their frequency counts for each Quality_Attribute that has errors in that week.
3. WHEN multiple weeks are selected, THE Dashboard SHALL display each week's findings in a separate, clearly labeled subsection headed with the week number (e.g., "Week 15").
4. THE Dashboard SHALL sort the week subsections in ascending chronological order by Transaction_Week number.
5. WITHIN each week subsection, THE Dashboard SHALL sort findings by Quality_Attribute group and then by descending frequency count within each group.
6. WHEN a single week is selected in the filter, THE Dashboard SHALL display that week's findings without a week header wrapper.
7. WHEN no error findings exist for a given week, THE Dashboard SHALL omit that week from the Common Findings display.
8. THE Dashboard SHALL display the week-wise Common Findings for all roles: Associate, Manager, and Admin.

### Requirement 2: Appreciation Email for Zero-Defect Associates

**User Story:** As a manager or admin, I want to send a pre-filled appreciation email to associates who achieved a 0% defect rate, so that I can recognize their quality performance efficiently.

#### Acceptance Criteria

1. WHEN the Associate-wise Summary table is rendered for a Manager or Admin, THE Dashboard SHALL display an "Appreciate" button next to each associate row where the Defect_Rate is exactly 0%.
2. WHEN a Manager or Admin clicks the "Appreciate" button, THE Dashboard SHALL open a Mailto_Link addressed to `{associateLogin}@amazon.com`.
3. THE Mailto_Link subject line SHALL follow the format: `Appreciation — 0% Defect Rate — Week {weekNumber}` where `{weekNumber}` is the currently selected Transaction_Week or the most recent week if multiple weeks are selected.
4. THE Mailto_Link body SHALL include: the number of audits monitored, the list of case IDs (transaction dates), the type of audit (disruption types), the week number, and the transaction dates for the associate's records in the selected scope.
5. WHILE an Associate is authenticated, THE Dashboard SHALL NOT display the "Appreciate" button in the Associate-wise Summary table.
6. WHEN multiple weeks are selected, THE Dashboard SHALL use the most recent Transaction_Week in the subject line and include data from all selected weeks in the body.

### Requirement 3: Feedback Email for Associates with Defects

**User Story:** As a manager or admin, I want to send a pre-filled quality feedback email to associates who have defects, so that I can share specific error details and help them improve.

#### Acceptance Criteria

1. WHEN the Associate-wise Summary table is rendered for a Manager or Admin, THE Dashboard SHALL display a "Feedback" button next to each associate row where the Defect_Rate is greater than 0%.
2. WHEN a Manager or Admin clicks the "Feedback" button, THE Dashboard SHALL open a Mailto_Link addressed to `{associateLogin}@amazon.com`.
3. THE Mailto_Link subject line SHALL follow the format: `Quality Feedback — Defect Rate {rate}% — Week {weekNumber}` where `{rate}` is the associate's Defect_Rate and `{weekNumber}` is the currently selected or most recent Transaction_Week.
4. THE Mailto_Link body SHALL include: the defect rate, the number of audits monitored, the list of case IDs (transaction dates), the type of audit (disruption types), the week number, the transaction dates, and the specific error details listing each failed Quality_Attribute with its auditor finding text.
5. WHILE an Associate is authenticated, THE Dashboard SHALL NOT display the "Feedback" button in the Associate-wise Summary table.
6. THE Mailto_Link body SHALL encode all special characters (line breaks, ampersands, equals signs) using URI encoding so that the email client renders the body correctly.

### Requirement 4: Feedback Tracking State Management

**User Story:** As a manager, I want to track which associates I have already shared feedback with, so that I can see at a glance who still needs to receive their quality feedback.

#### Acceptance Criteria

1. WHEN the Associate-wise Summary table is rendered for a Manager or Admin, THE Dashboard SHALL display a feedback status indicator next to each associate showing either "Pending" or "Shared".
2. THE Feedback_Tracker SHALL initialize all associates to "Pending" status for the current week by default.
3. WHEN a Manager or Admin clicks the "Appreciate" or "Feedback" email button, THE Feedback_Tracker SHALL update that associate's status to "Shared" for the current week.
4. THE Feedback_Tracker SHALL persist the sharing status in `localStorage` using a key scoped to the logged-in user's login and the Transaction_Week, so that each manager's tracking state is independent.
5. WHEN the Dashboard is reloaded, THE Feedback_Tracker SHALL restore the previously saved sharing status from `localStorage`.
6. FOR Transaction_Weeks prior to Week 15, THE Feedback_Tracker SHALL NOT display feedback status indicators.
7. FOR Transaction_Weeks from Week 15 onward, WHEN viewing a previous week's data, THE Feedback_Tracker SHALL display the status as "Completed" for all associates in that previous week, indicating the feedback cycle is closed.
8. THE Feedback_Tracker SHALL store data in the format `feedback_{managerLogin}_wk{weekNumber}` as the localStorage key, with a JSON object mapping associate logins to their status.

### Requirement 5: EMS Portal Link for Repeated Defaulters

**User Story:** As a manager or admin, I want to quickly open the EMS portal with pre-filled fields for repeated outliers, so that I can file performance actions without manually entering data.

#### Acceptance Criteria

1. WHEN the Repeated Defaulters section is rendered for a Manager or Admin, THE Dashboard SHALL display an "EMS" button next to each repeated defaulter's row.
2. WHEN a Manager or Admin clicks the "EMS" button, THE Dashboard SHALL open a new browser tab with the EMS_Portal new-item form URL.
3. THE EMS_Link SHALL include the following pre-filled query parameters: Team set to "OB", Week set to the current Transaction_Week formatted as "Week{number}" (e.g., "Week17"), Associate login from the Audit_Record data, Manager login (supervisorLogin) from the Audit_Record data, Region from the Audit_Record data, and EMS Category set to "Performance".
4. THE EMS_Link SHALL include a Case/WIMs ID parameter populated with the transaction dates or case identifiers from the associate's defect records.
5. THE EMS_Link SHALL include a Summary parameter populated with the complete feedback text derived from the associate's raw defect data, including failed Quality_Attributes and auditor findings.
6. THE EMS_Link SHALL leave the "Skip Manager" field empty for manual selection by the user.
7. THE EMS_Link base URL SHALL be: `https://share.amazon.com/sites/EMS%202.0/Lists/EMS%2020/Item/newifs.aspx` with the required List, Source, RootFolder, and Web query parameters.
8. WHILE an Associate is authenticated, THE Dashboard SHALL NOT display the "EMS" button in the Repeated Defaulters section.

### Requirement 6: Leadership Analysis Report — Visibility and Structure

**User Story:** As the admin, I want a comprehensive leadership analysis report section in the dashboard, so that I can review cross-region performance and share it with leaders.

#### Acceptance Criteria

1. WHILE an Admin is authenticated, THE Dashboard SHALL display a "Leadership Report" navigation tab or section.
2. WHILE a Manager or Associate is authenticated, THE Dashboard SHALL NOT display the "Leadership Report" section or any navigation element leading to it.
3. THE Leadership_Report SHALL include a week-wise performance summary covering both NA and EU regions, showing total audits, total defects, and Defect_Rate per region per week.
4. THE Leadership_Report SHALL include a manager-wise performance comparison table showing each manager's team Defect_Rate, total audits, and total defects for the selected period.
5. THE Leadership_Report SHALL include the list of Repeated_Defaulters with their defect week counts.
6. THE Leadership_Report SHALL include a defect trend summary showing the direction of Defect_Rate change over the last 4 weeks for each region.
7. THE Leadership_Report SHALL include a best practices section listing actionable guidance to avoid common RQM errors.

### Requirement 7: Leadership Report Export

**User Story:** As the admin, I want to copy or export the leadership report as formatted text, so that I can paste it directly into emails or documents for leadership sharing.

#### Acceptance Criteria

1. THE Leadership_Report section SHALL include a "Copy to Clipboard" button.
2. WHEN the Admin clicks the "Copy to Clipboard" button, THE Dashboard SHALL copy the complete Leadership_Report content to the system clipboard using the Clipboard_API.
3. THE copied content SHALL be formatted as readable plain text with clear section headers, aligned columns for tabular data, and line separators between sections.
4. WHEN the clipboard copy operation succeeds, THE Dashboard SHALL display a brief confirmation message (e.g., "Copied!") near the button for 2 seconds.
5. IF the Clipboard_API call fails, THEN THE Dashboard SHALL display an error message indicating the copy failed and suggest the user manually select and copy the content.
6. THE Leadership_Report section SHALL include an "Export" button that triggers a download of the report content as a `.csv` file containing the tabular data sections.

### Requirement 8: Mailto Link Generation and Encoding

**User Story:** As a developer, I want the mailto link generator to correctly encode all email fields, so that email content renders properly in Outlook regardless of special characters in the data.

#### Acceptance Criteria

1. THE Dashboard SHALL generate Mailto_Links using the format `mailto:{recipient}?subject={encodedSubject}&body={encodedBody}`.
2. THE Dashboard SHALL URI-encode the subject and body parameters using `encodeURIComponent` to handle special characters including ampersands, equals signs, line breaks, and Unicode characters.
3. FOR ALL valid associate summary data objects, generating a Mailto_Link and then decoding it with `decodeURIComponent` SHALL produce the original subject and body text (round-trip property).
4. WHEN the email body contains line breaks, THE Dashboard SHALL encode them as `%0D%0A` so that Outlook renders them as new lines.
5. WHEN the email body exceeds 2000 characters, THE Dashboard SHALL truncate the body to fit within the mailto URI length limit and append a note indicating the content was truncated.
